# ADR-0023: Framework Upgrade — ASP.NET Core / EF Core / Identity to .NET 10

**Status:** Accepted
**Date:** 2026-08-18
**Supersedes:** ADR-0002 (ASP.NET Core on .NET 8)
**Review date:** alongside the pilot retrospective (`docs/design/MVP-Implementation-Backlog.md`)

## Context

ADR-0002 selected .NET 8 (LTS) as the runtime for this system, at a time when .NET 8 was the current LTS release. **Management has since approved .NET 10 as the target framework**, ahead of Phase 1 foundation work starting. .NET 10 is itself an LTS release (.NET's even-numbered releases — 6, 8, 10 — are LTS; odd-numbered releases are Standard Term Support), so this upgrade moves from one LTS release to a newer one rather than trading LTS support away.

Per this project's ADR convention (`docs/architecture/README.md`'s "Conventions" section — "a later change to a recorded decision is captured as a new ADR that supersedes the old one... not by editing history in place"), this is recorded as a new ADR rather than an edit to ADR-0002.

## Decision

Adopt the following stack, superseding ADR-0002's .NET 8 selection. Every other technology ADR (0003 SQL Server/EF Core, 0004 Identity, 0013 Outbox, 0015 Hangfire, 0016 SignalR, 0017 attachment storage, 0021 testing strategy) is otherwise unchanged by this ADR — only the runtime/package versions those ADRs' chosen technologies run on are updated here.

| Component | Was (ADR-0002/0003/0004/0021) | Now |
|---|---|---|
| Runtime | .NET 8 (LTS) | **.NET 10 (LTS)** |
| Language | C# 12 | **C# 14** |
| Web framework | ASP.NET Core 8 | **ASP.NET Core 10** |
| ORM | EF Core 8 | **EF Core 10** |
| Identity | ASP.NET Core Identity 8 | **ASP.NET Core Identity 10** |
| Database | SQL Server (unchanged, ADR-0003) | SQL Server (unchanged) |
| Test framework | xUnit (unchanged, ADR-0021) | xUnit (unchanged — package versions below) |

**Every application project's `.csproj` sets:**

```xml
<TargetFramework>net10.0</TargetFramework>
<Nullable>enable</Nullable>
<ImplicitUsings>enable</ImplicitUsings>
<TreatWarningsAsErrors>true</TreatWarningsAsErrors> <!-- where practical; see Consequences -->
```

**Central Package Management** (`Directory.Packages.props` at the solution root) pins every package version once, rather than per-project — see `docs/design/MVP-Implementation-Backlog.md`'s Phase 1 foundation item for where this is introduced.

## Confirmed Package Versions (Verified Against a Real Restore and Build, Not Assumed)

Every version below was confirmed in this pass by actually installing the .NET 10 SDK in the build environment, generating real projects, and running `dotnet restore`/`dotnet build` against them successfully — not by reading a changelog:

| Package | Version | How confirmed |
|---|---|---|
| .NET SDK | **10.0.111** | `dotnet --info`/`dotnet --list-sdks` after installing `dotnet-sdk-10.0` via apt on the build environment's Ubuntu 24.04 base |
| ASP.NET Core runtime | 10.0.11 | `dotnet --list-runtimes` |
| `Microsoft.EntityFrameworkCore` | **10.0.11** | Real `dotnet add package` + `dotnet restore`/`build` against a `net10.0` class library — succeeded, 0 warnings/errors |
| `Microsoft.EntityFrameworkCore.SqlServer` | **10.0.11** | Same probe project; explicitly reported "compatible with all the specified frameworks" |
| `Microsoft.EntityFrameworkCore.Design` | **10.0.11** | Same probe project |

| `Microsoft.AspNetCore.OpenApi` | **10.0.11** | Generated by the SDK's own `dotnet new webapi` template targeting `net10.0` |
| `xunit` | **2.9.3** | Generated by the SDK's own `dotnet new xunit` template targeting `net10.0` — the SDK's own template is the authoritative "currently supported pairing," not a version chosen independently of it |
| `xunit.runner.visualstudio` | **3.1.4** | Same template generation |
| `Microsoft.NET.Test.Sdk` | **17.14.1** | Same template generation |

**No EF Core 8 package is mixed with an EF Core 10 package anywhere** — the probe build above used only 10.0.11 packages throughout, and Central Package Management (once introduced in Phase 1) makes a future accidental version mismatch a restore-time error rather than a silent inconsistency.

## Alternatives Considered

- **Stay on .NET 8** (rejected — supersedes management's explicit decision to move to .NET 10 ahead of Phase 1 starting).
- **.NET 9** (a Standard Term Support release, not LTS — rejected; .NET 10 is both newer and still LTS, so there is no support-horizon reason to prefer .NET 9).
- **xUnit v3 (`xunit.v3` package) instead of the classic `xunit` v2 package** — considered, since a `4.0.0` stable release of `xunit.v3` exists on NuGet. **Not chosen**: the .NET 10 SDK's own built-in project template still defaults to the classic `xunit`/`xunit.runner.visualstudio` v2 pairing confirmed above, which is the more conservative, currently-conventional choice for a new solution; nothing in this project's testing strategy (ADR-0021) requires xUnit v3's specific capabilities. Revisiting this is a reasonable future decision, not made here.

## Advantages

- .NET 10 LTS resets the support clock relative to .NET 8, which is approaching its own LTS midpoint — relevant given this system's multi-year, 7-year-retention operating horizon.
- C# 14 is available for any future code that benefits from it, without a second migration.
- Every package version pinned here was verified against a real restore/build in this pass, not assumed from a version-number pattern — reducing the risk of a Phase 1 foundation pass discovering a compatibility surprise on day one.

## Disadvantages

- Requires the .NET 10 SDK to be present in every environment that builds this solution (installed and confirmed in this pass for the current build environment; must be repeated for any other build/CI environment before Phase 1 code is built there).
- C# 14 / .NET 10 are newer than .NET 8 and carry marginally less accumulated production experience industry-wide, though this is a minor consideration for an internal pilot.

## Consequences

- `global.json` at the solution root pins the SDK version confirmed available in this build environment (**10.0.111**) — see `docs/design/MVP-Implementation-Backlog.md`'s Phase 1 foundation item, which introduces this file alongside the solution scaffolding.
- ADR-0002 is marked **Superseded by ADR-0023** and its text is left as a historical record, per this project's stated ADR convention — not edited in place.
- Any future ADR or design document that stated ".NET 8"/"EF Core 8"/"ASP.NET Core Identity 8" is updated to reference .NET 10/EF Core 10/Identity 10 as part of this same decision (see the file list in this ADR's companion commit).

## Risks

- Low — every package version recorded here was verified against a real restore and build in the actual build environment, not inferred; the only residual risk is that a *different* build/CI environment (not yet provisioned) may lack the .NET 10 SDK, which must be confirmed there before Phase 1 code is built in that environment too.
